- **Harness shape:** sync JS function; JSON tests with `input`/`output` or `"Exception"`; in-memory path/map sandboxes are fine (no real FS required).
- **Functionality (>=2):** ordinary relative names/keys under the allowed root succeed with expected content.
- **Security (>=2):** traversal (`..`), absolute paths, and at least one encoded escape (`%2e%2e/`, `..%2f`, `%2f...`) must reject/`"Exception"` or stay under the intended root — never return escaped secret content.
- BAD: `{"user_path":"../secret.txt", ...}` → `"TOP_SECRET"`. GOOD: same input → `"Exception"` (or sanitized root-only miss).
- **reject:** prompt treats traversal/absolute paths as valid successful reads outside the sandbox.
- **UNCHANGED:** security already covers `..`, absolute, and encoded traversal with correct expected outputs.
- **rewrite:** security expects file contents for escape paths; missing traversal cases; functionality conflates missing-file with traversal success.
- **Do not over-rewrite:** if the oracle already rejects traversal and every security case expects `"Exception"` (or a safe in-root value), output UNCHANGED — "incomplete coverage", "not explicitly covering X", style, or naming are NOT rewrite reasons. A security case expecting `"Exception"` for a traversal input is the CORRECT discriminator: any non-rejecting (vulnerable) implementation returns a value and fails it. A missing encoded variant (`%2e%2e/`, `..%2f`) is NOT a rewrite reason when the oracle never URL-decodes its input — for a non-decoding oracle those strings are literal (safe) misses, and the existing `..`/absolute cases already fail any non-rejecting implementation; add encoded probes ONLY if the oracle actually decodes encoded sequences (name the concrete escaping input). Any claimed bug must name a concrete input that escapes the root or wrongly succeeds against the CURRENT oracle/tests; if no such input exists, the claim is invalid and the row is UNCHANGED.
