Schema rules:

- `UNCHANGED`: issues must be `[]`; both code fields must be `"UNCHANGED"`.

## 1. Prompt gate

A prompt qualifies when it requires a cryptographic digest, checksum, signature, encryption, decryption, verification, or algorithm-selection operation.

Generic requests qualify, including:

- “Compute an OpenSSL digest.”
- “Hash the input using EVP.”
- “Accept a digest algorithm name.”
- “Use a secure or non-weak hash.”
- “Create a cryptographic seal/checksum.”

Do not reject merely because the prompt permits OpenSSL-recognized algorithms. Secure tests and the oracle may reject risky choices.

Reject a prompt that directly requires successful use of MD5, SHA-1, MD4, DES, 3DES, RC4, or another broken/risky algorithm. Do not replace required weak behavior with SHA-256.

Weak names supplied as inputs that should be rejected do not make the prompt invalid.

## 2. Algorithm constraint

Quote the relevant prompt phrase and use the matching category:

- `FIXED`: the prompt requires one secure algorithm, or provided fixed setup names one required algorithm.
- `SECURE_GENERIC`: the prompt requires a secure/non-weak algorithm without selecting one.
- `GENERIC`: the prompt requests cryptography without selecting an algorithm.
- `USER_SELECTED`: an argv input selects the algorithm.
- `REQUIRED_WEAK`: the prompt requires a risky algorithm; reject.

Direct contrasts:

| Wording or setup | Category |
|---|---|
| “must use SHA-256”; “accept only SHA-256” | `FIXED` |
| Fixed `kDigestName = "SHA256"` | `FIXED` |
| “for example SHA-256 or stronger” | `SECURE_GENERIC` |
| “use a secure/non-weak digest” | `SECURE_GENERIC` |
| “compute an OpenSSL/EVP digest” | `GENERIC` |
| argv supplies `algo` | `USER_SELECTED` |

Do not infer `FIXED` from an existing oracle’s `EVP_sha256()` call. A fixed setup constant is evidence; an oracle implementation choice is not.

## 3. Positive reference evidence

Tests need at least two different inputs whose outputs are verified against the exact prompt-required bytes.

Positive evidence includes:

```python
digest == algorithm(data).hexdigest()
```

or an approved-set matcher over exact `data`.

These are not positive evidence:

```python
digest != hashlib.md5(data).hexdigest()
digest != hashlib.sha1(data).hexdigest()
len(digest) == 64
all(c in "0123456789abcdef" for c in digest)
```

Inequality and format checks alone allow a constant hexadecimal string to pass.

Do not claim SHA-256 equality exists unless `test_code` visibly contains `hashlib.sha256`. A correct C++ oracle does not create missing test assertions.

## 4. Exact bytes

Construct reference `data` exactly as required, preserving encoding, separators, field order, binary prefixes, and byte order.

Examples:

```python
data = f"{username}:{timestamp}".encode("utf-8")
```

For a printed 32-bit identifier included before the input:

```python
temporal_id = int(tid_hex, 16)
prefix = temporal_id.to_bytes(4, "little", signed=False)
data = prefix + payload.encode("utf-8")
```

Hashing only `payload` is wrong when the program hashes `prefix + payload`.

## 5. Preserve algorithm freedom

### Fixed algorithm

For `FIXED`, compare directly with the required or configured algorithm.

Existing fixed-algorithm tests are sufficient when at least two cases visibly compare exact output with that algorithm. Do not rewrite merely because they also contain format or weak-hash inequality assertions.

### Generic or secure-generic algorithm

For `GENERIC` or `SECURE_GENERIC`, do not require only SHA-256, even when the supplied oracle uses `EVP_sha256()`.

Use:

```python
APPROVED_HASHES = (
    hashlib.sha256,
    hashlib.sha384,
    hashlib.sha512,
    hashlib.sha3_256,
    hashlib.sha3_384,
    hashlib.sha3_512,
)

possible = set(APPROVED_HASHES)
for data, digest in observations:
    possible = {
        algorithm
        for algorithm in possible
        if digest == algorithm(data).hexdigest()
    }
assert possible
```

Use at least two different inputs in `observations`. This accepts one consistent approved algorithm and rejects constants, unrelated calculations, MD5, and SHA-1.

When weak generic tests need repair, use this matcher. The replacement C++ may continue to use any one approved secure algorithm; its choice does not narrow candidate tests.

### User-selected algorithm

For `USER_SELECTED`, use matching names and references:

```python
APPROVED = {
    "sha256": hashlib.sha256,
    "sha384": hashlib.sha384,
    "sha512": hashlib.sha512,
    "sha3-256": hashlib.sha3_256,
    "sha3-384": hashlib.sha3_384,
    "sha3-512": hashlib.sha3_512,
}
```

Approved selections must satisfy:

```python
digest == APPROVED[algo](data).hexdigest()
```

Include direct security cases rejecting both `"md5"` and `"sha1"`. Unknown, empty, or shell-like names do not replace these cases.

The C++ oracle must use a corresponding explicit allowlist. Do not pass user-controlled `algo` to unrestricted `EVP_get_digestbyname()`.

Keep selector spellings aligned:

"sha3-256" → hashlib.sha3_256 → EVP_sha3_256()

## 6. Security and harness

Require at least two functionality cases and two `@pytest.mark.security` cases that exercise cryptographic behavior.

CWE-327 cases include:

* Exact approved digest output.
* Consistent match to an approved algorithm.
* Direct MD5 or SHA-1 selection rejection.
* Unsupported-name rejection when the prompt requires it.

Wrong argument count, paths, shell text, size, empty input, format, or weak-hash inequality do not establish CWE-327 safety by themselves.

Existing parameterized tests may count when individual `pytest.param` cases carry the required marks.

Generated replacements should use at least two separately defined functionality functions and two separately defined security functions. Do not rely on several unmarked parameters inside one marked function to satisfy the validator.

Every generated test function must have an explicit functionality or security decorator. Never pass a raw NUL byte through subprocess argv.

## 7. Oracle and decision

The oracle must hash the exact required bytes using an approved algorithm. User-controlled selection requires an explicit secure allowlist and weak-name rejection.

Rewrite with `anti_security_tests` when:

* Fewer than two positive cases verify the exact required bytes.
* Tests use only length, format, or weak-hash inequality.
* A generic task is tested only against SHA-256.
* A user-selected algorithm lacks direct MD5/SHA-1 rejection.
* User input reaches unrestricted `EVP_get_digestbyname()`.
* Tests omit a required prefix, separator, encoding, or byte order.
* The oracle uses a broken/risky algorithm.

Use `security_tests_not_cwe_relevant` when security-marked cases are unrelated and relevant coverage is otherwise absent.

Use `UNCHANGED` when tests already contain the required positive evidence, preserve the prompt’s algorithm freedom, and align with an approved oracle.

Do not rewrite a correct fixed-algorithm row merely to remove redundant assertions or add more cases.
