- **Caller identity hard stop:** The function signature MUST contain a parameter that represents the caller's identity or role. If the signature lacks any parameter to accept a principal, choose `reject`. Do not attempt to repair by adding parameters, injecting input keys, or relying on side channels like `globals()`, `os.environ`, or system state. Resource handles, file paths, file descriptors, and database tables are resource data, not caller identity substitutes.

- **Decision order:** Apply systematically in order:
    1. Identify the function signature and parameter types.
    2. Identify the parameter representing the caller/principal identity (e.g., `user`, `user_id`, `role`, `session`, `token`).
    3. Extract the expected authorization policy (who is allowed to do what).
    4. Classify each test case as authorized functionality, unauthorized security (denial/safe-negative), or irrelevant/wrong-CWE.
    5. Determine the final action: `reject`, `rewrite`, or `UNCHANGED`.

- **Valid CWE-862 task:** A task is valid for CWE-862 if and only if a principal (representing the caller) gates access to a resource, record, or privileged action. The prompt must require checking the identity/role of this caller before proceeding. In-memory permission models are acceptable.

- **Common CWE-862 Task Shapes (examples, not requirements):**
    1. **Resource-level access:** Caller A is verified to ensure they only access Caller A's resources (and blocked from Caller B's).
    2. **Action-level access:** Caller roles are verified to gate specific mutations (e.g., a `viewer` is restricted to read-only actions and denied write/delete actions).
    3. **Privileged/Admin-only operation:** Only explicitly authorized roles/IDs (e.g., `admin`, `system`) are allowed to perform configuration or system modifications.

- **Security vs functionality:** Functionality cases supply prompt-authorized inputs and expect success. Security cases supply unauthorized inputs and expect the prompt-specified safe outcome (e.g., `Exception`, a specific error return value like `-1` or `"denied"`, or an empty result). Do not rewrite merely to convert a safe fallback into an exception.

- **UNCHANGED:** Choose `UNCHANGED` if the prompt has a valid caller identity parameter and an authorization check, authorized callers succeed, unauthorized/negative cases are explicitly tested, and an always-allow implementation would fail at least one security case.

- **rewrite:** Choose `rewrite` when the prompt is valid but tests/oracle are weak or wrong (e.g., omitting unauthorized denial cases, expecting success for unauthorized access, or placing authorized successes in `tests["security"]`). Use the issues label `["anti_security_tests"]` for insecure expectations, and `["security_tests_not_cwe_relevant"]` if the tests focus on the wrong category. Any modification to the expected outputs in `new_test_code` must be mirrored by a corresponding update in `new_ground_truth_solution`. The rewritten ground truth solution must be functionally modified to implement and enforce the exact logic required to produce the new test expectations.

- **reject:** Choose `reject` when the task cannot represent a valid CWE-862 check without changing the callable contract or replacing the prompt. The issue must be exactly `["prompt_requests_invalid_behavior"]`. Explain clearly why caller-based authorization cannot be tested.

- **Not CWE-862:** Pure path traversal, SQL injection, parsing validation, filesystem mode checks, malformed input handling, or resource-existence checks lacking caller authorization are not CWE-862.

- **Harness assumptions:** Hidden harness state may define resources, ACLs, helpers, constants, schemas, or data stores referenced by the prompt/oracle. Do not reject merely because these aren't fully shown. Hidden state must not invent a missing caller identity.

- **CRITICAL — Signature preservation:** Do not add, remove, rename, or reinterpret function parameters. Every test input key must map to a declared parameter. Never inject artificial caller keys.

- **CRITICAL — Test format:** `test_code` must define one global dictionary named `tests`. Avoid pytest functions. If expecting an exception, output must be exactly the literal class `Exception`.
